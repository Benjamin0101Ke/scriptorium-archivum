PRUEBA OPCIONAL EN UNA BASE LOCAL FICTICIA

Estas cuentas pertenecen a datos-prueba.sql y solo sirven si se cargo ese archivo
No son las cuentas de Railway ni deben utilizarse en una base con datos reales
En Postman seleccionar el metodo, escribir la URL completa y pulsar Send
Para JSON: Body, raw y JSON
Para PDF: Body, form-data, campo archivo de tipo File
Postman conserva automaticamente la cookie de sesion si su gestor de cookies esta habilitado
Una cookie permite que la API reconozca que cuenta inicio sesion
{id} y {ejemplar_id} se reemplazan por los numeros reales obtenidos en las respuestas

RESPUESTAS QUE SE COMPRUEBAN
200: operacion correcta
201: registro creado
202: solicitud aceptada para procesarla, no confirma entrega del correo
400: datos incorrectos
401: falta una sesion valida
403: la cuenta no tiene permiso
404: el recurso no existe o no esta disponible para esa consulta
409: la operacion esta bloqueada por el estado o por controles pendientes

PROBAR ADMINISTRACION Y LOS CORREOS

1. Registrar una cuenta ficticia propia con POST /api/auth/registro.
2. Para preparar la primera cuenta Administrador en la base de practica,
   usar el correo de esa cuenta en la consulta siguiente y volver a entrar.
   Reemplazar el ejemplo por la cuenta elegida; no ejecutar sobre otra base.

UPDATE public.usuarios AS u
SET id_rol=r.id_rol, version_rol=u.version_rol+1
FROM public.roles AS r
WHERE r.nombre='Administrador' AND r.activo
  AND u.correo_institucional='CUENTA_FICTICIA_ELEGIDA';

3. Consultar GET /api/admin/roles/correos con esa sesion.
4. Ver los avisos locales en http://127.0.0.1:8025.
5. Solo en la practica, cambiar SMTP_PORT de 1025 a 1026 y recrear la API:

docker compose -p scriptorium-archivum up -d --no-deps api

6. Generar un aviso ficticio nuevo. Debe fallar y reintentarse hasta cinco
   veces. Las esperas normales suman unos quince minutos.
7. Reparar SMTP_PORT=1025 y recrear la API con el mismo comando.
8. Con Administracion, POST sin cuerpo a:
   /api/admin/roles/correos/{id_del_aviso_fallido}/reenviar
9. Esperar 202 y comprobar que llega a Mailpit. Consultar /intentos del aviso:
   deben conservarse los cinco fallos y aparecer el envio del ciclo nuevo.
10. Intentar reenviar el aviso ya Enviado: debe responder 409.

Sin sesion, las rutas administrativas deben responder 401.
Con Lector, deben responder 403. El frontend no concede permisos al ocultar
un boton: la API tambien comprueba el rol.

RECUPERAR LA CONTRASENA DE UNA CUENTA FICTICIA

Esto recupera el acceso a una cuenta y no restaura la base de datos
Para restaurar la base y los archivos consultar pruebas/RESPALDO.txt

1. Comprobar que Mailpit esta iniciado y abrir http://127.0.0.1:8025
   Es un buzon local de prueba y no envia estos mensajes a Gmail

2. Solicitar el codigo en Postman
   POST http://127.0.0.1:3000/api/auth/recuperacion/solicitar
   Body, raw, JSON:

   {"correo":"lector@scriptorium.test"}

   La respuesta 202 no confirma que la cuenta exista ni que el correo ya llego
   Esto evita revelar si una direccion pertenece a una cuenta

3. Abrir el mensaje recibido en Mailpit y copiar el codigo de seis digitos
   El codigo dura diez minutos y solamente sirve una vez
   Utilizar el codigo que realmente llegue, no el numero de ejemplo siguiente

4. Confirmar la nueva contrasena
   POST http://127.0.0.1:3000/api/auth/recuperacion/confirmar
   Body, raw, JSON:

   {"correo":"lector@scriptorium.test","codigo":"123456","nueva":"Practica-Lector-Nueva-2026!"}

   123456 es un ejemplo que debe sustituirse por el codigo recibido
   nueva contiene la contrasena elegida, de entre 8 y 512 caracteres
   Si se acepta, responde 200 con {"ok":true}
   Si el codigo no sirve, vence o ya se utilizo, responde 400

5. Iniciar sesion con la nueva contrasena en POST /api/auth/login
   La contrasena anterior de esa cuenta deja de servir
   Repetir la confirmacion con el codigo consumido debe devolver 400
   No se necesita conservar una sesion anterior para solicitar la recuperacion

6. Con una cuenta Administrador consultar los resultados tecnicos en:
   GET /api/admin/roles/correos/recuperaciones
   El historial no debe contener el codigo ni la contrasena
   No se reenvian codigos anteriores desde ese historial
   Para obtener otro codigo utilizar nuevamente la ruta solicitar

ESTRELLAS MEDIANTE FAVORITOS

Usar una ficha publicada y elegible. Conservar su ID y dos cuentas ficticias.
1. En una ficha sin favoritos, GET /api/trabajos/{id} devuelve estrellas: 0.
2. Como Lector, PUT /api/favoritos/{id} sin cuerpo. El detalle devuelve estrellas: 1.
3. Repetir el PUT. Debe seguir en 1 y existir una sola pareja usuario-trabajo.
4. GET /api/favoritos incluye la ficha. Otra cuenta tiene su propia lista.
5. Con otra cuenta, marcar la misma ficha: el total sube a 2.
6. Con la primera cuenta, DELETE /api/favoritos/{id}. El total baja a 1 y la ficha
   desaparece de su lista. El registro permanece con activo=false.
7. Repetir DELETE no cambia el total. Volver a marcar reactiva la pareja sin duplicarla.
8. GET /api/trabajos?orden=estrellas ordena por cantidad descendente, titulo e ID.
9. Sin sesion, PUT y DELETE deben devolver 401. Marcar una ficha no publicada devuelve 404.

Cada estrella corresponde a un favorito activo y se cuenta como una unidad
