RESPALDO Y RESTAURACION

1. QUE SE GUARDA

El respaldo permite recuperar los datos si se pierde o se dana una instalacion
Se guardan tres partes que deben corresponder al mismo momento:

- scriptorium.dump: tablas, datos, secuencias, restricciones y rutinas de PostgreSQL
- trabajos: PDF y anexos que estan en storage/trabajos
- claves: claves internas de proteccion de sesiones y codigos protegidos

Las fotos de perfil estan en PostgreSQL y se incluyen en el dump
El dump no incluye los PDF ni los anexos guardados fuera de la base
La carpeta de claves tampoco esta dentro del dump
.dump es la extension del archivo binario de respaldo, no un usuario ni una cuenta

El respaldo y cualquier configuracion privada se conservan fuera de GitHub
No se necesita crear un controller para respaldar o restaurar la base
Primero se practica la restauracion en una instalacion independiente

2. PREPARAR EL RESPALDO

Abrir PowerShell en backend, donde esta compose.yaml
Los comandos siguientes usan el proyecto Docker scriptorium-archivum
Si la instalacion tiene otro nombre, reemplazarlo en todos los comandos
Una variable como $destino guarda un valor para reutilizarlo en esa PowerShell
Usar la misma ventana hasta terminar el respaldo

Consultar los servicios:

    docker compose -p scriptorium-archivum ps

Iniciar PostgreSQL si esta detenido:

    docker compose -p scriptorium-archivum up -d postgres

Comprobar que ya acepta conexiones:

    docker compose -p scriptorium-archivum exec -T postgres pg_isready -h 127.0.0.1 -U postgres -d scriptorium_archivum

Repetir la comprobacion hasta que diga accepting connections
exec ejecuta dentro del servicio y -T evita una terminal interactiva
-h consulta al servidor del propio contenedor, -U indica usuario y -d la base
Esto no copia datos ni modifica tablas

Crear una carpeta nueva en Descargas:

    $descargas = (New-Object -ComObject Shell.Application).NameSpace('shell:Downloads').Self.Path
    $destino = Join-Path $descargas ('Respaldo-Scriptorium-' + (Get-Date -Format 'yyyy-MM-dd_HHmmss'))
    New-Item -ItemType Directory -Path $destino -ErrorAction Stop

La primera linea consulta a Windows la ubicacion real de Descargas
Join-Path une esa ubicacion con el nombre de la carpeta
Get-Date agrega fecha y hora para no mezclar el respaldo con uno anterior
New-Item crea la carpeta; ErrorAction Stop detiene el bloque si falla
No reutilizar una carpeta de respaldo anterior

3. COPIAR LA BASE, LOS ARCHIVOS Y LAS CLAVES

Durante esta parte la pagina no podra escribir mediante la API
PostgreSQL debe permanecer encendido para que pg_dump pueda leer la base
No permitir escrituras desde otros clientes mientras se toman estas copias

Ejecutar completo este bloque, incluidas sus llaves:

    $apiEncendida = @(docker compose -p scriptorium-archivum ps --status running --services) -contains 'api'
    if ($LASTEXITCODE -ne 0) {
        throw 'No se pudo consultar el estado de Docker'
    }
    docker compose -p scriptorium-archivum stop api
    if ($LASTEXITCODE -ne 0) {
        throw 'No se pudo detener la API'
    }
    try {
        docker compose -p scriptorium-archivum exec -T postgres pg_dump -U postgres -Fc -f /tmp/scriptorium.dump scriptorium_archivum
        if ($LASTEXITCODE -ne 0) {
            throw 'Fallo la creacion del respaldo de PostgreSQL'
        }
        docker compose -p scriptorium-archivum cp postgres:/tmp/scriptorium.dump "$destino/scriptorium.dump"
        if ($LASTEXITCODE -ne 0) {
            throw 'Fallo la copia del dump a Windows'
        }
        Copy-Item -LiteralPath './storage/trabajos' -Destination (Join-Path $destino 'trabajos') -Recurse -ErrorAction Stop
        docker compose -p scriptorium-archivum cp api:/home/app/.aspnet/DataProtection-Keys "$destino/claves"
        if ($LASTEXITCODE -ne 0) {
            throw 'Fallo la copia de las claves de proteccion'
        }
        Get-FileHash -LiteralPath (Join-Path $destino 'scriptorium.dump') -Algorithm SHA256 -ErrorAction Stop |
            Format-List | Out-File (Join-Path $destino 'comprobacion-dump.txt') -Encoding utf8 -ErrorAction Stop
        Get-ChildItem -LiteralPath (Join-Path $destino 'trabajos') -File -Recurse -ErrorAction Stop |
            Get-FileHash -Algorithm SHA256 -ErrorAction Stop |
            Export-Csv (Join-Path $destino 'inventario-archivos.csv') -NoTypeInformation -Encoding UTF8 -ErrorAction Stop
        docker compose -p scriptorium-archivum exec -T postgres rm -f /tmp/scriptorium.dump
        if ($LASTEXITCODE -ne 0) {
            throw 'La copia esta guardada pero no se pudo retirar el temporal del contenedor'
        }
    }
    finally {
        if ($apiEncendida) {
            docker compose -p scriptorium-archivum start api
            if ($LASTEXITCODE -ne 0) {
                Write-Warning 'Revisar Docker porque la API no pudo reiniciarse'
            }
        }
    }

Explicacion del bloque:

$apiEncendida recuerda si la API estaba funcionando antes del respaldo
--status running --services lista solamente los servicios encendidos
-contains 'api' comprueba si la API aparece en esa lista y guarda true o false
stop api detiene la API y mantiene PostgreSQL encendido
try contiene los pasos de copia
finally se ejecuta aunque falle la copia y devuelve la API a su estado anterior
Si estaba detenida antes de empezar, permanece detenida

pg_dump crea la copia logica de PostgreSQL
-Fc utiliza el formato de respaldo que despues puede leer pg_restore
-f guarda el archivo dentro del contenedor, en /tmp/scriptorium.dump
docker compose cp copia ese archivo binario a Windows sin convertir su contenido
No utilizar > para guardar el dump desde la salida de PowerShell

Copy-Item copia la carpeta de archivos y -Recurse incluye su contenido
La otra operacion cp copia las claves internas desde el contenedor de la API
El contenedor de API debe existir previamente, aunque este detenido
Las claves se conservan privadas porque protegen sesiones y codigos

Get-FileHash calcula una huella SHA256 para comprobar la integridad del archivo
Export-Csv guarda las huellas de los PDF y anexos para compararlos despues
LASTEXITCODE contiene el resultado del ultimo comando externo: cero indica exito
if revisa ese resultado y throw detiene la copia si encuentra un fallo
rm -f retira solamente el dump temporal del contenedor, no la copia de Windows

Al terminar debe existir en Descargas una carpeta con:

    Respaldo-Scriptorium-fecha_hora
        scriptorium.dump
        trabajos
        claves
        comprobacion-dump.txt
        inventario-archivos.csv

Un bloque que termino con error no se considera un respaldo completo
Conservar tambien la configuracion privada necesaria para reconstruir el entorno
Si se guarda .env junto al respaldo, no compartirlo ni subirlo al repositorio

4. PREPARAR UNA RESTAURACION SEPARADA

Descargar otra copia del proyecto en una carpeta nueva
Trabajar en backend de esa copia, nunca en la carpeta de la instalacion principal
Copiar .env.example a .env y completar las claves locales
Dejar API_PROJECT_PATH vacio para utilizar la API incluida en esa copia
Usar puertos libres diferentes, por ejemplo:

    POSTGRES_PORT=5443
    API_PORT=3010
    PGADMIN_PORT=5060
    MAILPIT_PORT=8030

Utilizar Mailpit en la restauracion para no enviar correos reales por accidente
Conservar SMTP_HOST=mailpit, SMTP_PORT=1025 y SMTP_TLS=false
Dejar SMTP_USER y SMTP_PASSWORD vacios en esta copia de practica

El nombre del proyecto de restauracion sera scriptorium-restore
Ese nombre hace que Docker cree otros contenedores y otros volumenes
No cambiarlo por scriptorium-archivum en los comandos siguientes
La carpeta storage/trabajos de esta copia tambien debe estar vacia

Crear en ese backend un archivo compose.restauracion.yaml con este contenido:

    services:
      api:
        environment:
          ConnectionStrings__Scriptorium: Host=postgres;Port=5432;Database=scriptorium_restaurada;Username=postgres

Este archivo cambia solamente la base utilizada por la API de la copia
Database=scriptorium_restaurada apunta a la base que vamos a restaurar
Los dos -f de los comandos siguientes combinan el Compose original y este ajuste
Usarlos juntos tambien al iniciar, detener o consultar esta instalacion de prueba

5. RESTAURAR EL DUMP

Abrir PowerShell en backend de la copia y seleccionar la carpeta del respaldo:

    $respaldo = 'C:\ruta\a\Respaldo-Scriptorium-fecha_hora'

Reemplazar el ejemplo por la carpeta real que contiene scriptorium.dump
No escribir aqui la ruta de la carpeta de la base principal

Iniciar solamente PostgreSQL de la restauracion:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml up -d postgres

Esperar a que su servidor acepte conexiones:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml exec -T postgres pg_isready -h 127.0.0.1 -U postgres -d postgres

Repetir esa comprobacion si todavia no acepta conexiones
Compose inicializa su base configurada, pero restauraremos en otra base nueva

Crear la base vacia de destino:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml exec -T postgres createdb -U postgres -T template0 -E UTF8 scriptorium_restaurada
    if ($LASTEXITCODE -ne 0) {
        throw 'No continuar: la base de destino no se pudo crear o ya existe'
    }

createdb crea la base, -T template0 utiliza una plantilla limpia y -E UTF8 fija su codificacion
La base debe ser nueva: no reutilizar una restauracion anterior ni borrar otra base

Copiar el dump al contenedor y restaurarlo:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml cp "$respaldo/scriptorium.dump" postgres:/tmp/scriptorium.dump
    if ($LASTEXITCODE -ne 0) {
        throw 'Fallo la copia del dump al contenedor de restauracion'
    }
    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml exec -T postgres pg_restore -U postgres --exit-on-error --no-owner -d scriptorium_restaurada /tmp/scriptorium.dump
    if ($LASTEXITCODE -ne 0) {
        throw 'La restauracion no termino correctamente; revisar antes de continuar'
    }
    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml exec -T postgres psql -X -v ON_ERROR_STOP=1 -U postgres -d postgres -c "ALTER DATABASE scriptorium_restaurada SET TimeZone TO 'America/El_Salvador';"
    if ($LASTEXITCODE -ne 0) {
        throw 'Fallo la configuracion de la zona horaria'
    }

pg_restore reconstruye los objetos y datos guardados por pg_dump
--exit-on-error detiene la restauracion al encontrar un error
--no-owner evita intentar asignar objetos a propietarios de otra instalacion
-d indica la base nueva que recibira el contenido del dump
El ultimo comando establece la zona horaria de la base restaurada
Estos comandos no modifican la base de la instalacion principal

6. RESTAURAR LOS ARCHIVOS Y LAS CLAVES

Comprobar que la carpeta de archivos de la copia esta vacia
Despues ejecutar:

    New-Item -ItemType Directory -Path './storage/trabajos' -Force -ErrorAction Stop
    Get-ChildItem -LiteralPath (Join-Path $respaldo 'trabajos') -Force |
        Copy-Item -Destination './storage/trabajos' -Recurse -ErrorAction Stop

Se copia el contenido de trabajos dentro de storage/trabajos
Los archivos deben quedar directamente alli, sin otra carpeta trabajos anidada
No mezclar los archivos restaurados con los de una instalacion anterior

Construir y crear el contenedor de API de la copia, sin iniciarlo:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml build api
    if ($LASTEXITCODE -ne 0) {
        throw 'Fallo la construccion de la API de prueba'
    }
    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml create --no-deps api
    if ($LASTEXITCODE -ne 0) {
        throw 'No se pudo crear el contenedor de API de prueba'
    }
    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml cp "$respaldo/claves/." api:/home/app/.aspnet/DataProtection-Keys/
    if ($LASTEXITCODE -ne 0) {
        throw 'No se pudieron restaurar las claves'
    }
    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml run --rm --no-deps --user 0 --entrypoint sh api -c 'chown -R "$APP_UID:$APP_UID" /home/app/.aspnet/DataProtection-Keys && chmod -R go-rwx /home/app/.aspnet/DataProtection-Keys'
    if ($LASTEXITCODE -ne 0) {
        throw 'No se pudieron ajustar los permisos de las claves'
    }

build prepara la imagen y create prepara el contenedor sin ejecutar la API
cp con claves/. copia el contenido de claves en el volumen de esta restauracion
run ejecuta un contenedor auxiliar para dar acceso a las claves al usuario de .NET
--user 0 se usa solamente para ajustar esos permisos en la copia
chown asigna el propietario y chmod quita el acceso de otros usuarios
--rm elimina ese contenedor auxiliar al terminar, sin borrar el volumen
Nunca copiar estas claves encima de las de la instalacion principal

Iniciar la API y el buzon de correo de prueba:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml up -d api mailpit

La API restaurada estara en http://127.0.0.1:3010 si se conservaron los puertos anteriores
El buzon de prueba estara en http://127.0.0.1:8030

7. COMPROBAR QUE EL RESPALDO SIRVE

Consultar /api/carreras y entrar con una cuenta que existia en la base respaldada
Comparar los conteos de usuarios y fichas con los de la copia original
Abrir diez fichas, si la base dispone de ellas, y comprobar sus PDF y anexos
Revisar autores, controles, permisos, favoritos y bitacora
Calcular SHA256 de los archivos restaurados y comparar cada nombre y huella
con inventario-archivos.csv; las rutas de carpeta pueden ser diferentes
Verificar que una cuenta sin permiso siga sin poder acceder a gestion de Biblioteca

Un dump creado sin errores no demuestra por si solo que la recuperacion este probada
La prueba termina cuando se verifica tambien la informacion y sus archivos
Para la aceptacion de RNF-06 se requieren dos copias consecutivas separadas por
hasta siete dias y el cotejo de diez fichas con sus archivos y controles
Si hay menos de diez fichas, documentar esa limitacion sin dar ese requisito por cumplido

Retirar el dump temporal de la restauracion despues de verificarla:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml exec -T postgres rm -f /tmp/scriptorium.dump

Para detener esta prueba sin borrar los datos restaurados:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml stop

Para retomarla despues:

    docker compose -p scriptorium-restore -f compose.yaml -f compose.restauracion.yaml start

Conservar siempre una copia privada del respaldo fuera de los contenedores
No ejecutar down -v sobre una instalacion que se quiera conservar
La recuperacion de contrasenas de usuarios se explica por separado en PRUEBA-GUIADA.txt
