CONSUMIR LA API

Recomiendo iniciar con la prueba de catalogos y sesion. Las rutas de ejemplo
usan el puerto 3000. Si se cambia en .env, ajustar el proxy del frontend.
No es necesario crear otra API ni copiar controllers al proyecto Angular.

Integración con Angular

Arranque en dos terminales

1. En el backend descomprimido sigue LEEME.txt. Comprueba que http://127.0.0.1:3000/api/carreras devuelve el catálogo de prueba.
2. En tu carpeta Angular, revisa frontend/proxy.conf.json o el archivo que pase tu comando npm start a Angular. Puedes adaptar proxy.conf.example.json. Ajusta el puerto si cambiaste API_PORT.
3. En la interfaz, utilizar su configuracion de conexion real para enviar las solicitudes a /api. Conservar el resto de la configuracion del frontend.
4. Con Node y npm compatibles con el package.json de tu proyecto, ejecuta npm ci y npm start desde la carpeta Angular que contiene package.json. Abre la dirección que imprime Angular. Reinicia el servidor de Angular al cambiar el proxy.
5. En la pestaña Red del navegador, comprueba que las solicitudes salgan a la misma dirección de la página con el prefijo /api. El proxy es el que se comunica con Docker. En otro equipo, 127.0.0.1 representa ese equipo, así que cada integrante puede levantar su propio backend.

En un despliegue compartido, configura el servidor web con HTTPS y proxy de /api hacia el backend bajo el mismo origen. El proxy de Angular CLI solo actúa en su servidor de desarrollo.

Sesión y formatos

- POST /api/auth/login recibe { "correo": "...", "password": "..." }. La respuesta contiene id, nombre, correo, rol y establece una cookie HttpOnly. Conserva las credenciales de la misma procedencia en fetch y evita guardar el password o la cookie en el código.
- POST /api/auth/registro recibe nombres, apellidos, correo, password. Sin carrera crea Lector; con id_carrera valido crea Estudiante. Puede incluir id_plan de esa carrera y abre sesion. Si el correo ya existe, responde 409.
- GET /api/auth/me recupera la sesión y el perfil. PUT /api/auth/perfil recibe los campos que se quieran cambiar entre nombre, avatar, tema. PUT /api/auth/contrasena recibe actual, nueva y renueva la sesión en ese navegador.
- POST /api/auth/logout cierra sesión. 401 corresponde a sesión ausente o inválida, 403 a cuenta sin permiso.
- Los cuerpos normales van como JSON. Para cargar PDF, usa FormData con un campo archivo y deja que el navegador genere el Content-Type.
- Para la vista previa y descarga, procesa la respuesta exitosa como binario o abre la URL autenticada. El método de la interfaz que lee siempre response.json() requiere una operación específica para respuestas PDF.
- En errores JSON, muestra error. Puede incluir fields, duplicate, bloqueos o controles. Los IDs de ficha y ejemplar viajan como cadenas. Los IDs de los catálogos y de personas pueden ser numéricos.

Ejemplos para adaptar en el proyecto de interfaz

const response = await fetch('/api/auth/login', {
  method: 'POST',
  credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ correo, password })
});
if (!response.ok) {
  const error = await response.json();
  throw new Error(error.error);
}
const usuario = await response.json();

const form = new FormData();
form.append('archivo', archivoSeleccionado);
const respuesta = await fetch('/api/admin/trabajos/' + id + '/pdf', {
  method: 'POST',
  credentials: 'same-origin',
  body: form
});
if (!respuesta.ok) {
  const error = await respuesta.json();
  throw new Error(error.error);
}
const { ejemplar_id } = await respuesta.json();

Rutas para cada equipo

Consulta pública y sesión - Uso
GET /api/carreras, /api/tipos-de-trabajo, /api/areas-tematicas - Catálogos
GET /api/trabajos, GET /api/trabajos/{id} - Resultados y detalle. Filtros q, autor, anio, carrera, area, tipo. Orden coincidencia, anio, titulo, estrellas
GET /api/trabajos/{id}/pdf?operacion=lectura o descarga - PDF con permiso por operación
GET /api/favoritos, PUT /api/favoritos/{id}, DELETE /api/favoritos/{id} - Favoritos de la sesión
GET /api/mis-envios, POST /api/mis-envios - Sesion Lector o Estudiante; requiere carrera guardada en el perfil. Consulta sus propias fichas. El alta recibe el PDF y los campos titulo, anio, resumen, id_carrera, id_tipo_trabajo, area_ids como FormData. La cuenta autenticada queda como autora y la ficha comienza En revisión

Biblioteca - Uso
GET /api/admin/personas, POST /api/admin/personas - Buscar ?q= y registrar con nombres, apellidos, identificador_institucional opcional
GET /api/admin/trabajos, POST /api/admin/trabajos, GET /api/admin/trabajos/{id}, PUT /api/admin/trabajos/{id} - Fichas. Campos titulo, anio, resumen, id_carrera, id_tipo_trabajo, area_ids, autor_ids. Para confirmar un duplicado usa confirmarDuplicado
POST /api/admin/trabajos/{id}/pdf - Máximo 25 MB y campo archivo. Devuelve ejemplar_id
POST /api/admin/trabajos/{id}/referencia - Referencia verificable con { "referencia": "..." }. Para PDF público se usa un archivo administrado
GET /api/admin/trabajos/{id}/pdf?ejemplar={ejemplar_id} - Vista previa autenticada. Si responde 404 después de una sustitución, recarga la ficha antes de verificar
PUT /api/admin/trabajos/{id}/controles - Ejemplo de campos (../pruebas/PRUEBA-GUIADA.txt). El detalle devuelve decision.fecha y decision.responsable
POST /api/admin/trabajos/{id}/publicar, POST /api/admin/trabajos/{id}/retirar - Publicar o retirar. Retiro recibe { "motivo": "..." }. Los controles fallidos devuelven 409
GET /api/admin/trabajos/{id}/enlaces, POST /api/admin/trabajos/{id}/enlaces, PATCH /api/admin/enlaces/{id}, DELETE /api/admin/trabajos/{id}/enlaces/{enlace} - Enlaces HTTPS. Alta con url, tipo, descripcion. Activar con habilitado. La eliminación necesita el ID de la ficha que contiene el enlace
GET /api/admin/bitacora, GET /api/admin/guia, GET /api/admin/reporte - Auditoría y consultas administrativas

Usa autor_ids y otorgante_ids seleccionados desde personas. Si cambia el correlativo UES, pide una confirmación nueva del depósito. Después de una suspensión, permite confirmar una decisión nueva y enviar registrar_decision: true en esa actuación. Muestra el estado y los motivos devueltos por la API.
Extensiones del perfil y de Administración

La API conserva las rutas existentes. Las siguientes extensiones requieren aplicar las migraciones 06, 07, 08 y 09 de sql-init.

Método y ruta - Acceso y comportamiento
GET /api/oferta-academica - Público. Devuelve departamentos, carreras y planes activos.
POST /api/auth/registro - Acepta los campos opcionales id_carrera e id_plan. Una carrera válida crea una cuenta Estudiante.
PUT /api/auth/perfil - Acepta carrera y plan. Una cuenta Lector que elige carrera pasa a Estudiante y recibe una cookie actualizada.
POST /api/auth/foto - Cuenta autenticada. Multipart con archivo, JPG o PNG de hasta 2 MB.
GET /api/auth/foto - Foto propia de la cuenta autenticada.
DELETE /api/auth/foto - Elimina la foto propia.
GET /api/admin/roles?q=&rol=&estado= - Administrador. Filtra cuentas y devuelve su nombre visible actualizado.
PUT /api/admin/roles/{id}/estado - Administrador. JSON habilitada, invalida las sesiones anteriores.
POST /api/admin/roles/{id}/recuperacion - Administrador. Solicita el correo de recuperación para esa cuenta.
GET /api/admin/roles/actividad - Administrador. Actividad reciente.
GET, POST /api/admin/catalogos/{tipo} - Administrador. Listar o crear carreras, departamentos, áreas temáticas o planes.
PUT /api/admin/catalogos/{tipo}/{id} - Administrador. Editar nombre, asociación y estado activo.
GET /api/trabajos/{id}/archivos - Remitente o Biblioteca ven todos. El público ve archivos autorizados del ejemplar vigente si el trabajo permite descarga.
POST /api/trabajos/{id}/archivos - Remitente o Biblioteca. Multipart con archivo y descripción. Queda pendiente de habilitación.
PATCH /api/trabajos/{id}/archivos/{archivo} - Biblioteca. JSON habilitado.
GET /api/trabajos/{id}/archivos/{archivo} - Descarga sujeta a los mismos permisos del listado.

Los valores de tipo son carreras, departamentos, areas-tematicas y planes. Los planes requieren id_carrera, nombre y activa, con url HTTPS opcional.

Estrellas y favoritos

Aplicar sql-init/14_estrellas_por_favoritos.sql despues de las migraciones anteriores.
Retira las valoraciones de 1 a 5 sin convertirlas en favoritos. Los favoritos existentes
conservan su estado. En una instalacion nueva ejecutar los SQL 01 a 14 en orden.

Metodo y ruta - Comportamiento
GET /api/trabajos?orden=estrellas - Ordena por cantidad de favoritos activos, titulo e ID.
GET /api/trabajos y GET /api/trabajos/{id} - Incluyen estrellas, un numero entero que empieza en cero.
GET /api/favoritos - Sesion requerida. Lista los favoritos activos y publicados elegibles de la cuenta.
PUT /api/favoritos/{id} - Sesion requerida, sin cuerpo. Marca o reactiva el favorito propio.
DELETE /api/favoritos/{id} - Sesion requerida, sin cuerpo. Desactiva el favorito propio sin borrar el registro.

Marcar dos veces no suma dos estrellas. Cada usuario aporta como maximo una por trabajo.
Al quitar el favorito deja de sumar y desaparece de la lista personal. Reactivarlo reutiliza
la misma pareja. Tras marcar o quitar, consultar el detalle para refrescar estrellas.
Las operaciones PUT y DELETE mantienen la respuesta {"ok": true}.

Las rutas /api/trabajos/{id}/valoracion y los campos valoracion_media y valoraciones_total
se retiraron. Cambiar el selector de orden a estrellas, quitar la puntuacion de 1 a 5 y
usar los endpoints de favoritos para el boton estrella. No se requiere otra tabla.

El catalogo mantiene los filtros existentes. La interfaz puede paginar su presentacion.

Tipos de trabajo

La migración 11_tipos_trabajo.sql agrega el estado activo y los tipos iniciales. El catálogo administrativo acepta el tipo tipos-trabajo en sus rutas GET, POST y PUT. El cuerpo usa nombre (máximo 60 caracteres) y activa. GET /api/tipos-de-trabajo devuelve los tipos activos. Las fichas existentes conservan su tipo aunque este se desactive.

Avisos por correo y docente asignado

Aplicar la migración 12_avisos_y_docentes.sql antes de desplegar esta API en una base existente. Las operaciones guardan su aviso en la misma transacción; el envío SMTP ocurre en segundo plano. Ver matriz de eventos y guía (../LEEME.txt).

- GET /api/admin/roles incluye docentes habilitados (id, nombre, correo), y cada cuenta incluye id_docente.
- PUT /api/admin/roles/{id}/docente acepta {"id_docente": 12}; null retira la asignación. Solo Administración; el destinatario debe ser Estudiante habilitado y el docente debe tener rol Docente revisor habilitado.
- GET /api/admin/roles/correos devuelve los últimos 100 avisos operativos, con destino, asunto, evento, estado, intentos y fechas; solo Administración. No devuelve códigos de recuperación ni claves SMTP.
- No se agregan permisos de publicación al docente ni se implementa un chat.

CORREOS: RUTAS DE ADMINISTRACION

Estas rutas requieren la cookie de una cuenta Administrador.
GET /api/admin/roles/correos
  Devuelve los ultimos 100 avisos: estado, ciclo, intentos y proxima ejecucion.
GET /api/admin/roles/correos/{id}/intentos
  Devuelve hasta 200 resultados del aviso, incluyendo ciclos anteriores.
POST /api/admin/roles/correos/{id}/reenviar
  Sin cuerpo. Solo acepta un aviso Fallido. Responde 202 y abre otro ciclo.
  Si el aviso esta Pendiente, Enviando, Enviado u Omitido, responde 409.
GET /api/admin/roles/correos/recuperaciones
  Devuelve resultados tecnicos, sin codigo, contrasena, cuerpo o destinatario.

Para conectar el boton Reintentar, mostrarlo solo cuando el estado sea Fallido.
Enviar el POST, mostrar que quedo pendiente y refrescar el listado.
El estado Enviado significa aceptacion por SMTP. No confirma lectura.
No se reenvia un codigo de recuperacion anterior desde este historial.

Sin sesion se recibe 401; sin permiso, 403; si no existe el aviso, 404.
No guardar contrasenas ni copiar cookies manualmente al codigo del frontend.
